# Zera Creative ERP — Project Reference

## Role
Lead Software Architect / Senior Full-Stack Engineer building Zera Creative's internal ERP platform. Long-term production system, not a prototype. Every decision favors scalability, maintainability, security, performance, and clean code over convenience. When multiple approaches are viable, pick the one common in mature enterprise software.

## Vision
Primary internal operating system for Zera Creative, gradually replacing internal tools while staying modular for future expansion. Feels like Linear/Notion/Slack/ClickUp (modern SaaS), functions like Odoo (ERP-style). Visual design: modern SaaS, not traditional ERP chrome.

## Core Principles
Clean Architecture, modular design, SOLID, maintainability, scalability, security, performance, readability, reusability, testability, strong DX. No unnecessary technical debt.

## Tech Stack

### Frontend — Flutter (single shared codebase)
- Platforms: Web, Android, iOS, Windows, macOS, Linux
- Material Design 3
- Responsive nav: Desktop = sidebar, Tablet = collapsible sidebar, Mobile = bottom nav
- Fonts: Poppins for all headings/titles/section titles/table headers/dialog titles/nav headings (heading font only). Inter (or similar) for body text.

## Authentication
- Company-email-only registration (`firstname.lastname@zeracreative.com`), no public registration

## RBAC
Flexible/configurable, not hardcoded. Default roles: Super Admin, HR/Manager, Team Lead, Employee. Must support custom roles without app-logic changes.

## Feature Modules (V1)
Role-specific dashboards (Employee/Team Lead/HR-Manager/Super Admin), Employee Management (full profile fields incl. profile completion %), Departments (no separate Teams concept — departments cover team groupings), Company Notices (targeting + read receipts + comments), Knowledge Base (Super Admin/HR-Manager/Team Lead author rich-text articles in-app; visibility targeting — Everyone/Specific roles/Specific departments/Roles+departments, union semantics; version history with editor + timestamp per revision; read in-app only, no downloads, uploads, search, tags, or favorites), Asset Management (QR/barcode, lifecycle, statuses: Available/Assigned/Repair/Lost/Retired), Employee Requests (Submitted → Manager Approval → HR Approval → Completed), Leave Management (approved by the employee's department head, then HR/Admin), Employee Onboarding/Offboarding Checklists (configurable step templates, auto-created on invite/status-change), Performance Reviews (one current review auto-created per employee at their most recent work-anniversary year — never backfills older missed years; configurable rating/text criteria; the employee's reporting manager or HR/Admin rates and completes it, employee adds an optional self-assessment, HR/Admin finalizes; year-by-year history per employee), Tasks Management (Super Admin/HR-Manager assign to any employee; a department head — the Team Lead role's authority, since there's no separate Teams concept — assigns only within their own department; single assignee per task with title/description/priority/due date/status — To Do/In Progress/Pending/Completed/Cancelled — freely self-updated by the assignee; comment thread; full change history; My Tasks/Assigned Tasks/Team Tasks views; no file attachments in v1), Feedback (incl. anonymous), Employee Directory, Notifications (in-app/email/push), Global Search, Admin Panel.

## Admin Business Management
Originally a six-module roadmap; shrank to **two modules** — Clients & Projects (+ Client Health, folded in) and Payroll — after Automations (2026-08-22) and then Agency Reporting and Finances (2026-08-23) were removed entirely, both per explicit instruction; then grew to **three** on 2026-08-23 with the addition of Leads (module 7 below), a new, explicitly-requested module built the same day, ahead of the standing "CRM is a future module, don't build it yet" rule elsewhere in this file — a direct, explicit override of that default, same as how every other item in this section only gets built once specifically asked for; then grew to **four** on 2026-08-25 with **Financial Reports** (module 8 below) — company-wide revenue/expense/profit reporting, i.e. exactly the thing the 2026-08-23 Finances removal said not to reintroduce "without the user asking again," which is precisely what happened. Clients & Projects, Payroll, and Leads are shared between Super Admin and HR/Manager (Employees and Team Leads still can't see or touch any of them), enforced via a dedicated permission per module (`clients.manage`, `payroll.manage`, `leads.manage`) granted to Super Admin implicitly (its "every known permission" grant) and to HR/Manager explicitly in `seed.ts` — never a hardcoded role check, so a custom role could still be granted any of these permissions later without code changes. **Financial Reports breaks that pattern deliberately**: it is Super-Admin-exclusive, since it exposes real company revenue/profit figures — a materially more sensitive surface than the other three. `main.dart`'s `_superAdminOnlyLabels` set (nav items hidden from HR/Manager even though they're admin-tier) was empty from 2026-08-23 until 2026-08-25 — left in place rather than deleted specifically so a future Super-Admin-exclusive module had somewhere to go without touching `ResponsiveScaffold`'s grouping mechanism — and now holds `{'Financial Reports'}`, its first member (see `_hrAndAdminOnlyLabels`, the set holding the other three modules and driving the "HR & Admin Features" heading one tier below "Admin Only Features" and above "General Features" on Super Admin's own sidebar).

5. **Automations** — built, then removed 2026-08-22 per explicit instruction ("remove automations feature and automations.. make sure everyone is notified for important stuff"). It originally shipped as a **fixed catalog** of 3 admin-toggleable automation types (Project Renewal Reminder, Task Deadline Reminder, Annual Leave Reset) plus an `AutomationExecutionHistory` audit table — see git history (`backend/src/features/automations/`, `frontend/lib/features/automations/`, migration `1788100000000-AddAutomations`) for the original design if ever needed again. 6. **Payroll** — done. `backend/src/features/payroll/`, `frontend/lib/features/payroll/`. A new, distinct `payroll.manage` permission. Reuses the pre-existing `SalaryRecord` entity (base salary + effective-dated history, already built for the employee profile's Salary History screen) rather than duplicating it — Payroll's own new pieces are a **formal, idempotent Payroll Run** (`PayrollRun`: month/year with a `UQ_payroll_runs_month_year` uniqueness constraint, status Draft → Finalized → Paid) and one `PayrollLineItem` per active employee per run (`baseSalary` snapshotted at generation time via a new `EmployeesService.getSalaryAsOf(employeeId, asOfIsoDate)` — the latest `SalaryRecord` whose `effectiveDate` is on or before the run's month-end, plain string comparison since dates are already 'YYYY-MM-DD' — plus one-off `allowances`/`overtime`/`deductions`/`advances`/`tax`/`fines`, all editable only while the run is Draft; `netPay` computed in the mapper, never stored). Deliberately **no recurring-item concept** (every adjustment is entered fresh per run) and **no formal loan ledger for advances** (a one-time entry, no balance/repayment automation) — both scoped down from the roadmap's original wording after confirming with the user, mirroring Automations' "fixed catalog over generic engine" restraint. `POST /payroll/runs` explicitly 409s on a duplicate month/year (an admin-triggered action, so a loud conflict beats silent dedup) rather than the daily-cron idempotency pattern used elsewhere. A Finalized/Paid run's line items are locked — the "permanent payment history" the roadmap named. No employee-facing payslip view — no self-service surface in V1 regardless of who can access the module. **Shared with HR/Manager since 2026-08-22** — `payroll.manage` is granted to both roles at seed time. Frontend: `PayrollPage` (run list + "Generate Payroll" month/year dialog) and `PayrollRunDetailPage` (run summary, Finalize/Mark Paid actions gated by status, a `DataTable` of line items — tapping a row while Draft opens an edit dialog for that employee's adjustment figures). Nav entry "Payroll" — coincides in name with the pre-existing Admin Dashboard's own "Payroll" stats section heading (`_SectionHeader('Payroll')`, unrelated), which is fine on-screen but meant two existing widget tests had to stop asserting on bare `find.text('Payroll')` in favor of the already-present, still-unique `'Monthly Payroll'` label. **`bonuses` removed, `fines`/`lateCount` added, 2026-08-26** per explicit instruction ("get rid of bonuses and add option to deduct late comings (3 lates = 1 unpaid off) and also add option to deduct fines") — migration `1789300000000-UpdatePayrollLineItems`. `fines` is a plain one-off amount, deliberately separate from the generic `deductions` field so fines stay distinguishable in the line-item table. `lateCount` is a plain entered count (no attendance-tracking module exists yet — Attendance is still a future module per this file) rather than derived from any real attendance data; the mapper computes `lateDeductionRs = floor(lateCount / 3) * (baseSalary / daysInMonth(run.year, run.month))` on every read, never stored, same "computed not persisted" convention as `netPay` — `netPay` itself now also subtracts `fines` and `lateDeductionRs`. **Superseded the same day** by a full second rework after the user pasted their real payroll spreadsheet (33 real employees, exact deduction/addition columns) with the instruction to match it exactly — every formula was reverse-engineered against every row of the real data via a verification script before any code changed, given real pay was at stake. Two convention changes from the first version above: `DAYS_PER_MONTH = 30`/`HOURS_PER_DAY = 8` are now **fixed constants**, not `daysInMonth(run.year, run.month)` — the real spreadsheet divides by a flat 30 regardless of the actual calendar month, so the mapper's `toPayrollLineItemResponse` no longer takes a `run` parameter at all. `lateCount` was renamed `lateDays` (same 3-for-1 unpaid-day rule, now against the flat daily rate) and four fields were added: `reimbursement`/`commissions` (plain one-off additions), `totalAbsent` (→ `absentDeductionRs = totalAbsent * dailyRate`), `lateHours` (→ `lateHoursDeductionRs = lateHours * hourlyRate`) — migration `1789400000000-AddPayrollAttendanceAndPieceRateFields`. The one genuinely ambiguous piece — a subset of employees paid `Quantity × Per-amount` instead of a fixed salary (confirmed via exact multiplication match against 5 real rows) — was put to the user via AskUserQuestion ("Manual entry per run" vs "Build Quantity/Rate as real fields"); **the user chose the more complex option**, so `PayrollLineItem` gained real `quantity`/`perUnitRate` columns, and the mapper's effective `baseSalary` becomes `quantity * perUnitRate` when both are set on a line item, else the `SalaryRecord` snapshot — computed on every read, never overwriting the immutable snapshot column. Frontend: the line-items `DataTable` grew to 19 columns (Base/Qty/Rate/Allowances/Overtime/Reimbursement/Commissions/Deductions/Fines/Absent/Absent Ded./Late Hrs/Late Hrs Ded./Late Days/Late Days Ded./Advances/Tax/Net Pay) and the edit dialog was reorganized into 4 labeled sections — "Piece-rate pay (optional)", "Additions", "Attendance deductions", "Other deductions" — each with inline helper text explaining the flat-30 and 3-for-1 rules.

**Freelancers added 2026-08-26, same day** — while reconciling the real July spreadsheet above, the user identified two of the "missing employee" rows (Hamza Saqib, Kulsum Zehra — both paid `quantity × per-amount`) as freelancers, not employees, and asked for a first-class way to add freelancers and pay them a variable monthly amount, plus a freelancer headcount stat "same as employees." Built as a new, deliberately lightweight standalone module `backend/src/features/freelancers/` (`Freelancer`: `fullName`, free-text `role`, `notes`, `isActive` — no department/designation/company-email, since freelancers never get an ERP login) rather than folding into Employee Management, mirroring this file's established "flat standalone entity, no relation to the heavier module" pattern (Leads vs. Client, Service vs. Project). Reuses `payroll.manage` — no new permission — since freelancer management only exists to serve Payroll.

Payroll integration keeps one unified `PayrollRun`/`PayrollLineItem` model rather than a parallel freelancer-payment concept, since the real spreadsheet lists freelancers in the exact same table with the exact same Total Net Salary math: `PayrollLineItem.employeeId` was made nullable and a nullable `freelancerId` FK added (migration `1789500000000-AddFreelancers`) — exactly one of the two is set per line item, enforced in `PayrollService`, not a DB constraint (mirrors `employeeId`'s own original lack of an FK constraint on this table). Unlike active employees, freelancers are **never auto-included when a run is generated** — a freelancer might not work every month, so an admin adds them to a specific run via a new `POST /payroll/runs/:runId/freelancer-line-items` (`AddFreelancerLineItemDto`: `freelancerId` + `baseSalary` entered directly + optional notes). Since a freelancer has no `SalaryRecord` to snapshot from, `baseSalary` itself becomes directly editable post-creation for a freelancer's line item only — `UpdatePayrollLineItemDto` gained an optional `baseSalary` field that `PayrollService.updateLineItem` rejects with a 400 if attempted on an employee's line item (protecting the immutable-snapshot invariant everywhere else). The mapper resolves `employeeName`/`employeePhotoUrl` from whichever of `employee`/`freelancer` is set and adds an `isFreelancer` flag to the response so the frontend knows which UI to show; `PayrollService.payRun`'s per-line-item notification loop skips freelancer line items (no `User`/login account to notify). The existing piece-rate `quantity`/`perUnitRate` override, and the full deductions/additions shape, are left available to freelancer line items unchanged — Hamza Saqib and Kulsum Zehra are both piece-rate freelancers, so the mechanism needed to keep working identically for them.

One real bug caught by this session's own "explicit `type` on nullable columns" lesson (documented in the first payroll rework's automations-era predecessor bug, see [[project-admin-business-modules-roadmap]]) recurring on the very next nullable columns added afterward: `Freelancer.role?: string | null` and the new `PayrollLineItem.employeeId?`/`freelancerId?: string | null` all crashed the backend on startup with `DataTypeNotSupportedError: Data type "Object"` until each got an explicit `@Column({ type: 'varchar' | 'uuid', nullable: true })` — reflect-metadata still can't infer a real Postgres type from a `X | null` union. Frontend: `frontend/lib/features/freelancers/` (full layered stack, no UI beyond what's described below), `PayrollPage` converted from a flat run list into a `DefaultTabController` with "Runs" and "Freelancers" tabs (roster list + Active/Inactive toggle + an Add/Edit dialog), `PayrollRunDetailPage` gained an "Add Freelancer" action (`FormSection` gained an optional `trailing` slot for this) and a "Freelancer" badge on freelancer rows in the line-items table; the edit dialog shows a directly-editable "This month's pay" field instead of the read-only "Salary snapshot" line when editing a freelancer's line item. Admin Dashboard's Admin Business Management section gained a `_TotalFreelancersCard` (active-freelancer count) alongside `_LatestPayrollRunCard`. Full regression: 356 backend tests (27 new) + `nest build` clean, 329 frontend tests (13 new) + `flutter analyze` clean. Live-verified end-to-end via the real backend (curl for freelancer creation and adding one to the real July run — the live browser's text-input automation was flaky for this specific dialog, a known environment limitation from earlier in this session, not a code defect, and the identical code path is covered by the passing widget-test suite using Flutter's own text-input simulation): Hamza Saqib's and Kulsum Zehra's real July amounts (27,300 and 5,000, matching their real 455×60 and 5×1000 piece-rate figures) were added to the actual July 2026 run, confirmed via the Freelancers tab, the run's line-items table (Base + "Freelancer" badge), the run list's total, and the Dashboard's "Total Freelancers: 2" tile all updating correctly and consistently.

**Radically simplified back down, 2026-08-26, same day** — per explicit instruction ("Make payroll little simpler. get rid of all the deductions, fines, absents etc. I want just employee name, base salary, net salary paid"), superseding essentially all of the deduction/attendance machinery built earlier the same day (the flat-30-day math, `reimbursement`/`commissions`/`totalAbsent`/`lateHours`/`lateDays`/`fines`/`deductions`/`advances`/`tax`/`allowances`/`overtime` — all removed). `PayrollLineItem` now carries only `baseSalary` (still an immutable per-employee SalaryRecord snapshot, or directly-entered for freelancers, unchanged), the optional piece-rate `quantity`/`perUnitRate` pair (kept deliberately — not a deduction, it's how Kulsum Zehra/Hamza Saqib/other real piece-rate employees' base pay is actually computed, confirmed against the real spreadsheet earlier the same day), and a new `netPay` — a **plain, directly-entered, stored** figure (no longer computed from a formula) that defaults to `baseSalary` when a line item is created and is then freely editable for every line item, not just freelancers'. Migration `1789600000000-SimplifyPayrollLineItems` backfills `netPay = ` the old full formula before dropping the 11 now-gone columns. Frontend: the line-items `DataTable` shrank from 19 columns back to 3 (Employee/Base/Net Pay); the edit dialog dropped its Additions/Attendance-deductions/Other-deductions sections, keeping only the (freelancer-only) Amount field, the Piece-rate pay section, and a new plain "Net Pay" field. Full regression: 351 backend tests + `nest build` clean, 327 frontend tests + `flutter analyze` clean.

This migration hit a real, live-data close call worth remembering generally: **this dev database has never actually gone through `migration:run`** — every schema change all session has landed via `synchronize: true` picking up entity edits automatically, so the `migrations` tracking table doesn't reflect reality and running `npm run migration:run` here fails immediately on the *first* migration file (`type already exists`, since that migration's `CREATE TYPE` was already applied by `synchronize` months ago, just never recorded). Worse: `synchronize: true` tried to add the new `netPay` column as `NOT NULL` directly against the real, already-populated July 2026 payroll run (27 live rows) and crashed the backend in a retry loop — Postgres correctly refused (`column "netPay" ... contains null values`) rather than silently corrupting data, and the failed `ALTER TABLE` was transactional and rolled back cleanly (confirmed via `\d payroll_line_items` showing the old schema fully intact before proceeding). Recovered by running this migration's exact `up()` SQL directly via `psql` — add `netPay` nullable first, `UPDATE` it from the old formula, `SET NOT NULL`, *then* drop the old columns — the same backfill-before-constrain pattern the migration file itself uses, just executed by hand since `migration:run` wasn't usable here. **Takeaway: in this dev environment, never trust `synchronize: true` to safely evolve a column from nullable-computed to `NOT NULL` (or any schema change needing a data backfill) on a table with real rows — write and manually execute the raw SQL (add nullable → backfill → constrain → drop) before letting the app reconnect, exactly like a real migration would.**

8. **Financial Reports** — done, 2026-08-25. `backend/src/features/financial-reports/`, `frontend/lib/features/financial_reports/`. ## Development Workflow
1. Understand the requirement.
2. Design the architecture.
3. Create/update the implementation plan.
4. Implement one feature/module at a time.
5. Keep the app compiling after every change.
6. Refactor when necessary.
7. Add tests where appropriate.
8. Update docs after each completed feature.

Never generate the whole app at once. Never break existing functionality when adding new features.

## Definition of Done
Compiles; follows project architecture; respects RBAC; validation implemented; loading states; empty states; error handling; responsive layouts; docs updated; no unnecessary duplication. Repository stays clean and production-ready after every change.
