# Zera Creative ERP — Project Reference

## Role
Lead Software Architect / Senior Full-Stack Engineer building Zera Creative's internal ERP platform. Long-term production system, not a prototype. Every decision favors scalability, maintainability, security, performance, and clean code over convenience. When multiple approaches are viable, pick the one common in mature enterprise software.

## Vision
Primary internal operating system for Zera Creative, gradually replacing internal tools while staying modular for future expansion. Feels like Linear/Notion/Slack/ClickUp (modern SaaS), functions like Odoo (ERP-style). Visual design: modern SaaS, not traditional ERP chrome.

## Core Principles
Clean Architecture, modular design, SOLID, maintainability, scalability, security, performance, readability, reusability, testability, strong DX. No unnecessary technical debt.

## Tech Stack

### Frontend — Flutter (single shared codebase)
- Platforms: Web, Android, iOS, Windows, macOS, Linux
- Material Design 3
- Responsive nav: Desktop = sidebar, Tablet = collapsible sidebar, Mobile = bottom nav
- Fonts: Poppins for all headings/titles/section titles/table headers/dialog titles/nav headings (heading font only). Inter (or similar) for body text.

### Backend
- REST API, PostgreSQL, JWT auth, RBAC, Docker, env-based config
- Repository Pattern, Dependency Injection
- Framework/language: **not yet decided — confirm with user before scaffolding**

## Authentication
- Company-email-only registration (`firstname.lastname@zeracreative.com`), no public registration
- Super Admin / HR add employees directly from the admin panel — no self-signup, no email invite (see "Add Employee" below)
- Email verification, password reset/change, session management, login history, device history, optional 2FA

## RBAC
Flexible/configurable, not hardcoded. Default roles: Super Admin, HR/Manager, Team Lead, Employee. Must support custom roles without app-logic changes.

## Feature Modules (V1)
Role-specific dashboards (Employee/Team Lead/HR-Manager/Super Admin), Employee Management (full profile fields incl. profile completion %), Departments (no separate Teams concept — departments cover team groupings), Company Notices (targeting + read receipts + comments), Knowledge Base (Super Admin/HR-Manager/Team Lead author rich-text articles in-app; visibility targeting — Everyone/Specific roles/Specific departments/Roles+departments, union semantics; version history with editor + timestamp per revision; read in-app only, no downloads, uploads, search, tags, or favorites), Asset Management (QR/barcode, lifecycle, statuses: Available/Assigned/Repair/Lost/Retired), Employee Requests (Submitted → Manager Approval → HR Approval → Completed), Leave Management (approved by the employee's department head, then HR/Admin), Employee Onboarding/Offboarding Checklists (configurable step templates, auto-created on invite/status-change), Performance Reviews (one current review auto-created per employee at their most recent work-anniversary year — never backfills older missed years; configurable rating/text criteria; the employee's reporting manager or HR/Admin rates and completes it, employee adds an optional self-assessment, HR/Admin finalizes; year-by-year history per employee), Tasks Management (Super Admin/HR-Manager assign to any employee; a department head — the Team Lead role's authority, since there's no separate Teams concept — assigns only within their own department; single assignee per task with title/description/priority/due date/status — To Do/In Progress/Pending/Completed/Cancelled — freely self-updated by the assignee; comment thread; full change history; My Tasks/Assigned Tasks/Team Tasks views; no file attachments in v1), Feedback (incl. anonymous), Employee Directory, Notifications (in-app/email/push), Global Search, Admin Panel.

## Explicitly Excluded from V1
AI Assistant/Chat/Suggestions/Automation/generated content. Storage usage dashboard/quotas/analytics/monitoring. Keep architecture extensible for these later.

## Future Modules (design for, don't build yet)
CRM, Client Portal, Project Management, Attendance, Payroll, Recruitment, OKRs, Internal Chat, Time Tracking, Expense Claims, Finance, SEO Dashboard, Automation Engine, Company Calendar, Training Portal, Rewards & Recognition, Company Wiki.

## Admin Business Management
Originally a six-module roadmap; shrank to **two modules** — Clients & Projects (+ Client Health, folded in) and Payroll — after Automations (2026-08-22) and then Agency Reporting and Finances (2026-08-23) were removed entirely, both per explicit instruction; then grew to **three** on 2026-08-23 with the addition of Leads (module 7 below), a new, explicitly-requested module built the same day, ahead of the standing "CRM is a future module, don't build it yet" rule elsewhere in this file — a direct, explicit override of that default, same as how every other item in this section only gets built once specifically asked for; then grew to **four** on 2026-08-25 with **Financial Reports** (module 8 below) — company-wide revenue/expense/profit reporting, i.e. exactly the thing the 2026-08-23 Finances removal said not to reintroduce "without the user asking again," which is precisely what happened. Clients & Projects and Payroll are shared between Super Admin and HR/Manager (Employees and Team Leads still can't see or touch any of them), enforced via a dedicated permission per module (`clients.manage`, `payroll.manage`) granted to Super Admin implicitly (its "every known permission" grant) and to HR/Manager explicitly in `seed.ts` — never a hardcoded role check, so a custom role could still be granted any of these permissions later without code changes. **Financial Reports and Leads both break that pattern deliberately**: each is Super-Admin-exclusive — Financial Reports since it exposes real company revenue/profit figures, Leads since 2026-08-28 per explicit instruction ("make leads, admin only feature") even though it carries no comparably sensitive figures itself — a materially more restrictive surface than the other two, in Leads' case a deliberate tightening rather than a data-sensitivity call. `main.dart`'s `_superAdminOnlyLabels` set (nav items hidden from HR/Manager even though they're admin-tier) was empty from 2026-08-23 until 2026-08-25 — left in place rather than deleted specifically so a future Super-Admin-exclusive module had somewhere to go without touching `ResponsiveScaffold`'s grouping mechanism — held `{'Financial Reports'}` alone from 2026-08-25 until 2026-08-28, and now holds `{'Financial Reports', 'Leads'}` (see `_hrAndAdminOnlyLabels`, the set holding the other two modules and driving the "HR & Admin Features" heading one tier below "Admin Only Features" and above "General Features" on Super Admin's own sidebar).

6. **Payroll** — done. `backend/src/features/payroll/`, `frontend/lib/features/payroll/`. A new, distinct `payroll.manage` permission. Reuses the pre-existing `SalaryRecord` entity (base salary + effective-dated history, already built for the employee profile's Salary History screen) rather than duplicating it — Payroll's own new pieces are a **formal, idempotent Payroll Run** (`PayrollRun`: month/year with a `UQ_payroll_runs_month_year` uniqueness constraint, status Draft → Finalized → Paid) and one `PayrollLineItem` per active employee per run (`baseSalary` snapshotted at generation time via a new `EmployeesService.getSalaryAsOf(employeeId, asOfIsoDate)` — the latest `SalaryRecord` whose `effectiveDate` is on or before the run's month-end, plain string comparison since dates are already 'YYYY-MM-DD' — plus one-off `allowances`/`overtime`/`deductions`/`advances`/`tax`/`fines`, all editable only while the run is Draft; `netPay` computed in the mapper, never stored). Deliberately **no recurring-item concept** (every adjustment is entered fresh per run) and **no formal loan ledger for advances** (a one-time entry, no balance/repayment automation) — both scoped down from the roadmap's original wording after confirming with the user, mirroring Automations' "fixed catalog over generic engine" restraint. `POST /payroll/runs` explicitly 409s on a duplicate month/year (an admin-triggered action, so a loud conflict beats silent dedup) rather than the daily-cron idempotency pattern used elsewhere. A Finalized/Paid run's line items are locked — the "permanent payment history" the roadmap named. This migration hit a real, live-data close call worth remembering generally: **this dev database has never actually gone through `migration:run`** — every schema change all session has landed via `synchronize: true` picking up entity edits automatically, so the `migrations` tracking table doesn't reflect reality and running `npm run migration:run` here fails immediately on the *first* migration file (`type already exists`, since that migration's `CREATE TYPE` was already applied by `synchronize` months ago, just never recorded). Worse: `synchronize: true` tried to add the new `netPay` column as `NOT NULL` directly against the real, already-populated July 2026 payroll run (27 live rows) and crashed the backend in a retry loop — Postgres correctly refused (`column "netPay" ... contains null values`) rather than silently corrupting data, and the failed `ALTER TABLE` was transactional and rolled back cleanly (confirmed via `\d payroll_line_items` showing the old schema fully intact before proceeding). Recovered by running this migration's exact `up()` SQL directly via `psql` — add `netPay` nullable first, `UPDATE` it from the old formula, `SET NOT NULL`, *then* drop the old columns — the same backfill-before-constrain pattern the migration file itself uses, just executed by hand since `migration:run` wasn't usable here. **Takeaway: in this dev environment, never trust `synchronize: true` to safely evolve a column from nullable-computed to `NOT NULL` (or any schema change needing a data backfill) on a table with real rows — write and manually execute the raw SQL (add nullable → backfill → constrain → drop) before letting the app reconnect, exactly like a real migration would.**

Both deltas are reconstructed entirely from data that already exists — **no new snapshot table, no cron job** — since the two domains already carry enough history:

- **Active employees** (`EmployeesService.getActiveEmployeeDelta`, `GET /employees/stats/active-delta?days=7`, `employees.read`): combines the current employee list with every "Employment Status" `EmployeeAuditLog` change recorded since the cutoff (`AuditLogRepository.findFieldChangesSince`, new). An employee whose own `createdAt` is after the cutoff didn't exist yet, so they count as "not active back then" regardless of current status — this is what makes a new hire who's active today correctly show up as part of the +1, rather than being excluded from both sides of the comparison as a wash.
- **Pending performance reviews** (`PerformanceReviewsService.getPendingReviewsDelta`, `GET /performance-reviews/pending-delta?days=7`, `performance.manage`): `pendingNow` (count with `status == PENDING`) minus `pendingAsOfCutoff` — a new `PerformanceReviewRepository.countPendingAsOf(cutoff)` querying `createdAt <= cutoff AND (completedAt IS NULL OR completedAt > cutoff)`. Exact, not an approximation, because `completedAt` is a one-way marker in this schema — `unfinalizeReview` reverts `FINALIZED` back to `COMPLETED`, never back to `PENDING`, so a review can never re-enter the pending state once `completedAt` is set.

**2026-09-09**, after a multi-step research/scoping conversation ("is there option to email directly to anybody from here" → confirmed no email capability existed at all → "Is there a way we can make functionality for send and receive emails?" → "instead of email, can it integrate my existing web hosting system?" → confirmed the user's mail lives on Verpex shared cPanel hosting → "each employee will have their own mailbox" → asked about auto-provisioning via cPanel's UAPI → the user chose the lighter option instead: *"how about for lighter version, we integrate their emails in the system? This is deliberately **not** auto-provisioning — mailboxes are created by hand in cPanel first, then their real address/password are entered into the ERP so the app can authenticate as that mailbox over standard SMTP (send) and IMAP (receive).

**The one deliberate exception to this project's "never store real passwords" precedent.** Every earlier instance of this question (see the data-import case) ended with the user choosing NOT to store real credentials, reference-only fields instead. A mailbox is unusable without the app being able to authenticate with it, so that option doesn't exist here — flagged to the user up front rather than silently building around it. Mitigation: `EmailAccount.encryptedPassword` is AES-256-GCM ciphertext (`credential-crypto.util.ts`, key from a new `EMAIL_CREDENTIAL_KEY` env var, generated once for this dev environment and never committed to a public place), decrypted only in-memory for the duration of a single SMTP/IMAP call, and the plaintext password is never returned by any API response (`EmailAccountResponse` has no password field at all, verified by a dedicated `email.service.spec.ts` test that asserts the ciphertext never appears in `getMyAccount`'s output).

**New `email.manage` permission**, granted to Super Admin (implicitly) and HR/Manager — same split as `goals.manage`/`EmployeeOfTheMonth`: it only gates setting up or removing a mailbox *on behalf of another employee*. Every employee (Team Lead and plain Employee included, and HR/Admin too since they're employees as well) can already set up, edit, and use their own mailbox through `EmailController`'s unguarded `/account/me`, `/send`, `/inbox` routes — no permission needed for your own mailbox, mirroring `GoalsController`'s `/me`/`/team` self-scoped pattern.

**Backend**: `nodemailer` for SMTP send, `imapflow` + `mailparser` for IMAP receive (list headers live from the server on every request — no local sync/cache of message content, keeping this genuinely "lighter"). `EmailService.sendMail` opens a fresh `nodemailer` transport per send using the viewer's own decrypted credentials; `listInbox`/`getMessage` open a fresh `ImapFlow` connection per call, always against `INBOX` only. All mailbox-server failures (wrong password, unreachable host) collapse to a generic `BadRequestException` rather than leaking IMAP/SMTP internals to the frontend.

**Frontend**: new `EmailPage` — shows a setup form ("Set up your mailbox") when the viewer has no `EmailAccount` yet; once configured, shows an inbox list (click a row for a detail dialog with the full body), a Compose dialog, and a settings gear that re-opens the same form pre-filled (password field blank — must be re-entered to change it, since the stored value can't be decrypted back to display). An `email.manage` holder additionally sees a "Manage a mailbox for another employee" section — an employee picker plus the same setup form, scoped to whichever employee is selected. New "Email" nav destination, visible to every role (not in `_adminOnlyLabels`) — same visibility rule as "Goals".

## Roles & Permissions shared with HR/Manager, with two new guard rails

**2026-09-11**, per explicit instruction ("roles should be editable by HR as well (she cant edit admin role but anything below admin and HR)") — `roles.manage` added to HR/Manager's grant in `seed.ts` (previously Super-Admin-exclusive, alongside `finances.manage`/`leads.manage`/`users.impersonate`, which all remain Super-Admin-only). This is a direct instruction, but granting it exposed two real gaps the research pass surfaced before writing any code — neither existed as a concern while only Super Admin held `roles.manage` (an all-permissions holder editing anything is a no-op restriction-wise), but both become real the moment a non-unrestricted role gets this permission:

**A `roles.manage` holder can't edit the Super Admin role itself** unless they personally hold every known permission — `RolesService.assertCanEditSuperAdminRole` (new, `roles.service.ts`), checked at the top of `updateRole` whenever `role.name === 'Super Admin'`. Matched by name rather than a new flag, since Super Admin is the one seeded role that already implicitly holds every permission (`seed.ts`) — nothing else in this app singles out a role by name, so this stays a narrow, explicitly-scoped exception rather than a precedent. `RolesController.update`/`.create` gained `@CurrentUser() caller: JwtPayload` (previously unused in this controller) to make the check possible.

**Nobody can grant a role a permission they don't personally hold** — `RolesService.assertCallerHoldsPermissions` (new), checked on every `createRole` and on `updateRole` whenever `permissionKeys` changes. This is what actually stops HR/Manager from, say, editing the "Employee" role to grant it `finances.manage` — a privilege-escalation path that would otherwise open the moment `roles.manage` stopped being Super-Admin-exclusive, since nothing before this checked the caller's own permissions against what they were assigning to someone else. **Only newly-added permissions are checked** — `updateRole` diffs the requested `permissionKeys` against the role's current ones first (`currentKeys`/`newlyGrantedKeys`), so a role that already carries a permission the caller doesn't hold (granted earlier by someone with broader access) can still be edited for anything else, or have that specific permission *removed*, without the whole save being rejected. Getting this diff wrong first (checking the full final list, not just what's new) would have been a real usability bug — any edit to a role that happened to carry so much as one permission outside the caller's own set would otherwise become permanently unsaveable by that caller, even a plain description change.

Frontend (`role_permissions_page.dart`) mirrors both server-side checks so a `roles.manage` holder doesn't fill out a form only to hit a 403: a new `viewerIsUnrestrictedProvider` (`role_providers.dart`, compares the viewer's own permissions against the full `permissionsProvider` list) disables the Super Admin row's Edit button with an explanatory tooltip when the viewer isn't unrestricted; `_PermissionCheckboxList` disables checking any permission box the viewer doesn't hold, *unless* it was already on the role when the dialog opened (`_RoleFormDialogState._originalKeys`, frozen at `initState` — the same newly-granted-only distinction as the backend), so unchecking (or re-toggling) a pre-existing permission always stays possible regardless of who's editing.

Unlock state lives in a plain `StateProvider<Set<String>>` (`unlockedModulesProvider`, keyed by a short module slug) — deliberately **session-scoped, not persisted** to local storage, so the PIN is required again on the next app load, matching "lock this data by PIN" read literally as re-entry rather than a one-time unlock. Each module has its own independent entry in that set — unlocking Leads does not unlock Financial Reports. Since `ModulePinGate` only builds `child` once unlocked, the wrapped page's own data-fetching providers don't fire until the PIN is entered — a side benefit given this app's `IndexedStack`-based nav otherwise builds every section's root widget eagerly at app start.

## Development Workflow
1. Understand the requirement.
2. Design the architecture.
3. Create/update the implementation plan.
4. Implement one feature/module at a time.
5. Keep the app compiling after every change.
6. Refactor when necessary.
7. Add tests where appropriate.
8. Update docs after each completed feature.

Never generate the whole app at once. Never break existing functionality when adding new features.
